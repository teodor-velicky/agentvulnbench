# Path codebook for rater 2

Assign each row exactly ONE label: P1..P8 or `none`. Classify by the *route from attacker-controlled input to host impact* that the advisory describes, not by the row's class keyword alone. If two paths seem to fit, choose the one whose **entry + missing guard** match best, and say so in the reason. Use `none` only when no path's attacker position, entry and sink fit.

Guard shapes: absent / incomplete / ignored / differential (gate parses differently from executor) / misplaced (guard on one branch/direction/default only).

| Label | Name | Attacker position | Entry | Missing guard | Sink | Impact |
|---|---|---|---|---|---|---|
| P1 | Model output into an interpreter | Untrusted content (document, web page, tool result, chat) steers the agent's model; attacker never types the payload into the app | A completion or tool-call string produced by the model | No parser limiting model output to the feature's safe shape (absent or ignored) | `exec`, `eval`, or a subprocess running Python | Code execution as agent/server process |
| P2 | Hand-rolled gate parses differently from the executor | Usually model-mediated (code/shell tool); sometimes an authenticated low-privilege user who writes a flow or expression | Code, shell command, or env/config map passing through a framework-written filter | A gate that agrees with the executor: denylist, regex, AST check or prefix allowlist that reads input differently from the real interpreter/shell/npm (incomplete or differential) | Real executor: Python `exec`, `sh -c`, `npm`/`npx`, `str.format`, JS sandbox | Sandbox escape to host code execution |
| P3 | Model-chosen tool argument escapes file/repo confinement | Prompt-injected model picks args of a file or repo tool; MCP host forwards as is | A `path` / `file_path` / `repo_path` tool argument | Containment against the granted root (absent, bare prefix match, `abspath` instead of `realpath`, one direction only) | Filesystem read/write or `git` operation outside the granted root | Arbitrary file write (then code exec) or file/secret read |
| P4 | Repository or artefact at rest trusted as code | Whoever authored a repo, model repo, dataset shard, checkpoint store or prompt template that the agent/server later opens | `.git/config`, model `auto_map`/config, pickled cache entry, Jinja chat template | Loader treats the artefact's own configuration as trusted: no `trust_remote_code` check, no config hardening, pickle by default | `git` running a configured program, dynamic module import, `pickle.load`/`torch.load`, unsandboxed Jinja | Code execution as server user, often during a read-only operation |
| P5 | Serialized object crosses a trust boundary | Mainly a network peer reaching a serving data-plane/API port; variant: model output carrying a serializer marker | Bytes on a KV-transfer/ZMQ/HTTP socket, client-chosen media type, or an `lc` dict in model-produced message fields | No auth on the channel plus too-wide binding, with deserialization; or no escaping of user-controlled serializer markers | `pickle.loads`, `recv_pyobj`, `torch.load`, or a reviver reading `os.environ` | RCE on serving nodes or env-secret theft |
| P6 | Control plane trusts its network position | Outsider who can reach the port; for loopback dev tools, a web page the developer visits (cross-origin, DNS rebinding) | HTTP/WebSocket request to an agent server, MCP transport or gateway | Authentication or Origin/Host binding: absent, off by default, fail-open, configured but never enforced, unanchored/prefix Origin match | Whatever the control plane exposes: code validation, flow builds, stdio command spawn, MCP tool calls | Unauthenticated RCE or tool execution |
| P7 | Malicious MCP server turns client into confused deputy | An MCP server (or its OAuth metadata) the user's client connects to | OAuth authorization-server metadata, `authorization_endpoint` URL, resource/audience value, server-supplied schemas | Issuer/resource binding (RFC 8707 audience), URL-scheme validation before `open()`, consent bound to the browser | Credentials sent to attacker's token endpoint, or OS command via system URL opener | Client-secret theft, token reuse across servers, command exec on client host |
| P8 | Fetch guard lets attacker URL into the internal network | Outsider or low-privilege user supplying a URL, or a web page the agent's crawler / a model-chosen fetch follows | A URL in a file-typed input, media URL, crawled link, webhook or tool argument | Resolve-and-check on every hop: (a) no check, (b) no DNS resolution, (c) redirects not re-checked, (d) address encodings, (e) rebinding TOCTOU, (f) guard/fetcher URL-parser differential | Server-side HTTP client | SSRF into internal services / cloud metadata |
| none | Fits no path | — | — | — | — | Use for rows whose attacker position, entry and sink match none of the above (e.g. a bug with no host-level impact, or an authz/info-leak bug outside every path) |

Source: definitions condensed from the authors' outline of the paper's path definitions (path headers and the Attacker position / Entry / Missing guard / Sink / Impact bullets). Row assignments from the draft are deliberately NOT part of this codebook.
